# 애자일 턴/그리드 전략 게임용 md 문서 구조 설계

> 이 프로젝트(뱀서류 토이프로젝트)가 아닌 **다른 프로젝트**(유니티 턴/그리드 기반 전략 게임, 애자일 개발 방식)에 적용할 문서 구조 설계안.
> 작성 배경: 뱀서 토이프로젝트의 `Docs/` 구조는 `game-design.md`를 최상위 SoT로 두고 `feature-spec.md`가 하위를 라우팅하는 톱다운 구조인데, 애자일하게 시스템이 수시로 생기고 없어지는 프로젝트에는 자주 바뀌는 게임 디자인이 문서 트리의 "뿌리"가 되는 게 오히려 방해가 된다고 판단해 새로 설계함.

## 요구사항 요약

- **뿌리(절대 안 바뀜)**: 코드 규약, 턴/그리드 핵심 시스템·아키텍처
- **잎(자주 바뀜)**: 게임 디자인, 승패 조건, 하위 시스템들
- **그대로 가져갈 것**: `feature-spec` 패턴 (챕터별로 "해당 파일만 열어서" 구현하는 방식)
- 슬래시 커맨드도 계속 사용

확정한 3가지 구조적 결정:
1. **산출물 형태**: 실제 프로젝트가 정해지면 이 설계를 그대로 파일로 스캐폴드
2. **아키텍처 vs 컨벤션**: `architecture.md`(턴/그리드 핵심 시스템·인터페이스 계약, 거의 불변)와 `convention.md`(네이밍·코드 스타일, 상대적으로 안정적이지만 조정 가능)를 **분리**
3. **하위 시스템 생애주기**: `feature-spec/active/` + `feature-spec/archive/` **폴더로 물리적 분리**, 폐기된 스펙은 목차에서도 제외

---

## 1. 전체 트리

```
<새 프로젝트 루트>/
├─ CLAUDE.md                     ← 뿌리: 세션 진입점 (거의 불변)
└─ Docs/
   ├─ architecture.md            ← 뿌리: 턴/그리드 핵심 아키텍처 (절대 불변)
   ├─ convention.md               ← 뿌리: 코드 스타일 규약 (안정적, 미세조정 가능)
   ├─ feature-spec.md             ← 목차: active 시스템만 나열
   └─ feature-spec/
      ├─ active/                 ← 잎: 현재 살아있는 시스템 스펙
      │  ├─ win-condition.md
      │  ├─ unit-stats.md
      │  └─ ...
      └─ archive/                ← 잎(폐기): 버려진 시스템 스펙, 목차 제외
         └─ old-win-condition.md
```

`game-design.md` 같은 단일 기획서는 **의도적으로 루트/뿌리에 두지 않는다.** 대신 "왜 이 시스템이 이런 모양인가"는 각 `feature-spec/active/*.md` 챕터 파일 안에 그 시스템 고유의 설계 의도로 **분산 내장**한다 — 이렇게 하면 시스템이 바뀌거나 폐기될 때 그 디자인 근거도 자연스럽게 같이 바뀌거나 archive로 같이 넘어간다. 다만 "장르 한 줄, 플레이어 수, 핵심 판타지" 정도의 **1페이지 미만 스냅샷**은 있으면 신규 세션 온보딩에 도움이 되므로, 원하면 `Docs/vision.md`로 아주 가볍게(10줄 이하) 유지하는 것을 권장 — 이것도 거의 안 바뀌는 수준까지 압축했을 때만 뿌리 쪽에 둘 가치가 있다.

## 2. 문서별 역할 (SoT 원칙 유지)

| 문서 | 뿌리/잎 | 역할 | 변경 빈도 |
|---|---|---|---|
| `CLAUDE.md` | 뿌리 | 페르소나·톤·"언제 뭘 읽을지" 라우팅·작업분담·커맨드 목록 | 거의 없음 |
| `Docs/architecture.md` | 뿌리 | 턴 진행 상태머신, 그리드 좌표계, 턴/그리드 핵심 인터페이스(예: `ITurnActor`, `IGridOccupant`), 제공 인프라(싱글톤·이벤트버스 등) | 절대 불변 (프로젝트 전체의 물리 법칙) |
| `Docs/convention.md` | 뿌리 | 네이밍, `[SerializeField] private`, 폴더 위치, 기본 C# 컨벤션 — **아키텍처 계약은 담지 않음** | 안정적, 드물게 조정 |
| `Docs/feature-spec.md` | 라우팅 | active 챕터 목차 테이블만 | active 목록이 바뀔 때마다 |
| `Docs/feature-spec/active/*.md` | 잎 | 시스템별 구체 스펙 + 그 시스템의 설계 의도(왜) | 수시로 |
| `Docs/feature-spec/archive/*.md` | 잎(폐기) | 폐기된 스펙, 폐기 사유·일자 헤더 포함 | 이동 후 고정 |

원본 프로젝트의 `convention.md`는 "코드 스타일 + 인터페이스 계약 + 제공 인프라"를 한 문서에 뭉쳐뒀지만, 이번엔 **변동성이 다른 두 축이라 분리**한다: 인터페이스·아키텍처는 시스템 전체가 그 위에서 동작하므로 바뀌면 파급이 크고(뿌리), 네이밍·스타일은 국소적으로 바뀌어도 다른 시스템에 영향이 적다.

## 3. `architecture.md`를 보호하는 톤 규약 (CLAUDE.md에 반영)

원본 CLAUDE.md의 "명세서와 다른 길로 가게 되면 차이를 먼저 알려주고 진행"은 `convention.md`·`feature-spec`에는 그대로 적용하되, **`architecture.md`는 한 단계 더 엄격하게**:
- `convention.md`/`feature-spec` 위반 가능성 → 차이를 짚고 **진행**
- `architecture.md` 위반 가능성 → 차이를 짚고 **사용자 승인 전까지 진행 중단** (뿌리는 실수로 조용히 깨지면 파급 범위가 다르기 때문)

이 비대칭을 CLAUDE.md의 "응답·소통 톤" 섹션에 명문화하는 것을 권장.

## 4. active → archive 생애주기 & 챕터 파일명 규칙

- 원본은 번호 접두사(`01-input.md` ~ `14-build.md`, 구현 순서 고정)를 썼지만, 애자일 환경에서는 시스템이 수시로 끼어들고 빠져서 번호가 쉽게 깨진다. → **번호 대신 영문 slug만 사용** (`win-condition.md`, `unit-stats.md`). 순서가 필요하면 `feature-spec.md` 목차 테이블의 행 순서로 표현.
- `feature-spec.md` 목차 테이블에 **상태 컬럼**(예: `experimental`/`stable`)을 추가해 "검증 중인 시스템"과 "굳어진 시스템"을 구분 — 완전히 폐기되기 전에 있는 중간 상태를 표현.
- 시스템을 버릴 때: 파일을 `active/`에서 `archive/`로 이동 + 파일 상단에 `> 폐기일: YYYY-MM-DD · 사유: ...` 헤더 추가 + `feature-spec.md` 목차에서 해당 행 제거. git history가 있으니 archive 파일 자체는 이력 설명용 헤더 한 줄이면 충분(원본처럼 상세 변경 이력을 문서화할 필요 없음).

## 5. 슬래시 커맨드 설계 (원본 패턴 재사용)

원본의 "첫 인스턴스를 손으로 만든 뒤 반복 패턴을 커맨드로 추출" 원칙은 그대로 유지. 이번 구조에 맞춰 역할이 다른 커맨드 3종을 제안(전부 지금 만들 필요는 없고, 실제 반복이 확인된 뒤 하나씩 추출):

| 커맨드 | 역할 | 원본 대응 |
|---|---|---|
| `/add-system` | `feature-spec/active/`에 새 시스템 스펙 스캐폴드 생성, `architecture.md` 계약 위반 여부 먼저 확인 | `/add-enemy`, `/add-weapon` |
| `/archive-system` | 시스템을 `active/`→`archive/` 이동 + 목차 갱신 + 폐기 헤더 삽입까지 자동화 | (원본엔 없음 — 애자일 생애주기 전용 신규 커맨드) |
| `/convention` | 코드가 `convention.md`(스타일)·`architecture.md`(아키텍처 계약) 위반했는지 검토 전용 | `/convention` |

`/archive-system`은 이 프로젝트 특성(시스템이 자주 죽는다)에서만 값어치가 있는 커맨드라 원본엔 없던 것을 새로 제안한 것 — 실제로 "버리는 일"이 반복되기 시작하면 손으로 몇 번 해본 뒤 추출.

## 6. CLAUDE.md "작업 전 읽기" 섹션 변경점

원본 대비 읽는 순서·비중이 바뀐다:
- `architecture.md` — 새 시스템이 턴/그리드와 맞닿는 지점을 설계할 때 필독. 한 번 숙지하면 자주 안 바뀌므로 매번 재확인할 필요는 낮음.
- `convention.md` — 원본과 동일, 코드 작성 전 항상.
- `feature-spec.md` → `active/` 해당 챕터 1개만 — 원본 원칙("매번 전부 읽지 말 것") 그대로 유지.
- `archive/`는 기본적으로 안 읽음 — 과거에 왜 이 방식을 버렸는지 참고가 필요할 때만 명시적으로 요청.

## 후속 작업 (미확정)

문서 3종(`architecture.md`/`convention.md`/`feature-spec` 템플릿)의 실제 내용은 새 프로젝트의 턴/그리드 시스템이 구체화된 뒤 채워야 한다. 지금은 뼈대·역할·생애주기 규칙만 확정한 상태이며, 실제 새 프로젝트 경로가 정해지면 이 구조 그대로 스캐폴드 파일을 생성할 수 있다.
